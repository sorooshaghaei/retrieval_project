\section{Introduction}

Information retrieval is the task of ranking documents so that the most relevant ones appear first for a user query. In this project we work with a large technical corpus and a set of labeled training queries. The assignment is divided into two phases. Phase 1 focuses on basic retrieval with classical and neural methods. Phase 2 adds category classification and asks how the classifier can be used to improve retrieval.

\begin{itemize}
    \item dataset loading and statistical exploration;
    \item construction of a normalized \texttt{content} field;
    \item three retrieval models: TF-IDF, BM25+, and Sentence-Transformer embeddings;
    \item embedding inspection through matrix shapes and a 2D projection;
    \item evaluation with Recall@K, Precision@K, and MRR@K;
    \item category classification for both documents and queries;
    \item classifier-aware reranking for Phase 2;
    \item Kaggle submission export.
\end{itemize}

\section{Final Changes and Reasons}

The final version differs from our earlier drafts in five main ways.

\begin{enumerate}
    \item \textbf{Ground-truth parsing now matches the real qrels schema.} The competition qrels store relevant items under \texttt{relevant\_doc\_ids} with nested \texttt{doc\_id} entries. Without this fix, Recall, Precision, and MRR could be computed against empty relevance sets. The notebook now also raises an error if qrels parsing produces empty relevance, misses labeled queries, or references document ids that are not in the corpus.
    \item \textbf{Category-wise sampling is now stable with the current pandas behavior.} The notebook uses a sampling pattern that keeps the \texttt{category} column during visualization and downsampling. This avoids the grouped-sampling issue that was breaking category-aware plots and classifier preparation.
    \item \textbf{The report now separates labeled-query evaluation from Kaggle submission runs.} Only the training queries have visible qrels, while the Kaggle test queries are unlabeled. Because of that, the report keeps offline Stage 2 analysis separate from the later submission run.
    \item \textbf{The discussion now focuses more on the main behaviors than on the full hyperparameter history.} Earlier drafts put too much emphasis on one supposedly ``current'' Stage 2 configuration. The revised version focuses instead on the patterns that stayed consistent across later experiments: strong embedding recall, useful reranking, harmful hard filtering, and small gains from a soft category bonus.
    \item \textbf{The final report keeps three pieces of evidence separate.} The best offline Stage 2 result comes from \texttt{retrieval-evaluation.ipynb}; the current submission setup comes from \texttt{src/config.py} together with \texttt{kaggle-submission.ipynb}; and the public score \(0.62419\) comes from the leaderboard.
\end{enumerate}

\subsection{Previous tries, failures, and lessons}

\paragraph{Baseline retrieval attempts.}
\begin{itemize}
    \item \textbf{TF-IDF baseline.} The model was simple and useful as a first sanity check, but lexical overlap alone was not enough for many relevant query-document pairs. In the end, TF-IDF stayed useful as a baseline, not as our final retriever.
    \item \textbf{BM25+ lexical upgrade.} BM25+ improved over TF-IDF and handled document-length variation better, but it still stayed clearly behind embeddings on recall and rank quality. We kept it as our strongest lexical reference point rather than our final Stage 1 model.
\end{itemize}

\paragraph{Notebook and pipeline failures.}
\begin{itemize}
    \item \textbf{Grouped sampling instability.} A grouped pandas sampling pattern sometimes dropped the \texttt{category} column and triggered notebook errors such as \texttt{KeyError: category}. The fix was to switch to stable category-preserving downsampling for visualization and classifier preparation.
\end{itemize}

\paragraph{Lessons that shaped the final report.}
\begin{itemize}
    \item \textbf{Query classifier with \texttt{text + tags}.} The classifier became extremely accurate because the query tags are almost category-pure in the labeled split, so they behave a lot like label-revealing metadata. For that reason, we keep this caveat visible and discuss the classifier mainly through its effect on retrieval decisions rather than presenting the raw setup as a headline result.
    \item \textbf{Evaluation depth vs.\ submission depth.} Later notebooks and the current code defaults do not all use exactly the same depth values. So the offline evaluation, the current submission defaults, and the public Kaggle result need to be reported separately. What matters most in practice is how depth changes coverage, reranking reach, runtime, and score interpretation.
\end{itemize}

\section{Preprocessing and Content Construction}

The assignment asks for a new text field called \texttt{content}. The notebook uses the following policy:
\begin{itemize}
    \item documents: \texttt{title + text + tags};
    \item retrieval queries: \texttt{title + text};
    \item classifier queries in the active notebook: \texttt{title + text + tags}.
\end{itemize}

So the project uses different query views for retrieval and for Stage 2 classification. Retrieval stays close to the original query wording through \texttt{title + text}, while the category classifier also uses \texttt{tags}. This helped the practical submission pipeline, but it has to be interpreted carefully because the query tags are highly informative about category in the labeled data.

The shared normalization steps are:
\begin{itemize}
    \item lowercasing;
    \item replacement of the separators \texttt{-}, \texttt{\_}, and \texttt{/} with spaces;
    \item whitespace collapsing;
    \item trimming leading and trailing whitespace.
\end{itemize}

For lexical methods, tokenization uses the pattern \texttt{[a-z0-9]+}, and English stopword filtering is enabled by default.

\section{Phase 1: Retrieval Models}

\subsection{TF-IDF retrieval}

TF-IDF stands for \emph{term frequency--inverse document frequency}. It gives high weight to terms that appear frequently in one document but are relatively rare in the collection. In vector-space retrieval, each document and query is represented by a sparse TF-IDF vector, and documents are ranked by cosine similarity with the query vector.

Conceptually, TF-IDF is useful because it is simple, fast, and often surprisingly competitive as a baseline. Its main limitation is that it depends strongly on lexical overlap. If a relevant document uses different wording from the query, TF-IDF may fail even when the underlying meaning is similar.

\subsection{BM25+ retrieval}

BM25+ is a probabilistic lexical ranking model. It improves over naive bag-of-words weighting by:
\begin{itemize}
    \item saturating term frequency contributions;
    \item normalizing for document length;
    \item adding a positive lower-bound adjustment through the BM25+ variant.
\end{itemize}

BM25+ is often stronger than plain TF-IDF when document lengths vary substantially, as is the case in this corpus. However, BM25+ remains a lexical model and therefore still depends on token overlap.

\subsection{Embedding retrieval}

Dense embeddings map text into high-dimensional vectors that encode semantic information. In this project we use the Sentence-Transformer model \texttt{all-MiniLM-L6-v2}. Documents and queries are embedded into a 384-dimensional space, and cosine similarity is computed through normalized dot products.

Embeddings can help retrieval because they are more robust to synonyms, paraphrases, and broader semantic similarity. Their main tradeoffs are higher computational cost, larger memory usage, and the risk of retrieving semantically related but not strictly relevant documents.

\section{Evaluation Measures}

The notebook implements the three required retrieval metrics:
\[
\text{Recall@K} = \frac{\# \text{relevant retrieved documents}}{\# \text{relevant documents}}
\]
\[
\text{Precision@K} = \frac{\# \text{relevant retrieved documents}}{\# \text{retrieved documents}}
\]
\[
\text{MRR@K} = \frac{1}{\text{rank of the first relevant document}}
\]

For Phase 1 comparison, the notebook also reports runtime and average latency per query. For Phase 2, it augments the retrieval summary with classifier accuracy, and computes a combined score as
\[
\text{CombinedScore} = \frac{1}{4}\left(\text{Recall} + \text{Precision} + \text{MRR} + \text{Accuracy}\right).
\]

\section{Phase 1 Experimental Protocol}

Only \texttt{queries\_train.json} has relevance labels, while \texttt{queries\_test.json} is the unlabeled competition test set. So in the final notebook run we use \textbf{all 327 labeled training queries} as the offline evaluation set for retrieval. We do not introduce an additional query-side validation split.

Phase 1 compares TF-IDF, BM25+, and embeddings over the grid
\[

\section{Phase 2: Category Classification}

\subsection{Classifier model and input features}

In the notebook, we use a \textbf{TF-IDF + LinearSVC} classifier. This is a reasonable choice for a five-class text classification problem, and it is simple enough to train and evaluate quickly. The input features are:
\begin{itemize}
    \item document classifier text: \texttt{title + text + tags};
    \item query classifier text for diagnostics and submission-time hints: \texttt{title + text + tags}.
\end{itemize}

For the clean standalone classification benchmark, the notebook trains on an \textbf{80/20 stratified document split} with \texttt{random\_state=42}. Queries are \emph{not} mixed into that training split. They are only used later as a diagnostic transfer test.

\subsection{How accuracy is computed}

The notebook computes accuracy as
\[
\text{Accuracy} = \frac{\# \text{correct category predictions}}{\# \text{examples in the evaluation set}}.
\]
This definition is used both for the held-out document benchmark and for the diagnostic query-side comparison.

These results point to five main conclusions.

\begin{enumerate}
    \item \textbf{The best overall offline result is the embedding retriever with reranking and a soft category bonus.} It reaches a combined score of \(\mathbf{0.635325}\) with MRR \(=0.648262\).

\subsection{Cross-encoder reranker diagnostics}

The supplementary notebook \texttt{reranker-evaluation.ipynb} gives a useful closer look at the reranker. On category-filtered embedding candidates, it improves the combined score from \(0.568914\) to \(0.608709\), which again shows that reranking helps the ordering near the top of the list. At the same time, the notebook also shows concrete failure cases.

\begin{enumerate}
    \item \textbf{Its main benefit is rank repair, not candidate discovery.} MRR rises sharply while Recall usually stays fixed, which is exactly the signature of a reranker working on an already-strong candidate set.
    \item \textbf{Average gains do not prevent per-query failures.} The reranker notebook includes a query for which the first relevant document is pushed down from rank \(1\) to rank \(30\), even though the reranked system is better on average.
    \item \textbf{The classifier is safest as a soft signal.} The reranker diagnostics and the full Phase 2 table agree that a weak category bonus is helpful, while aggressive hard filtering can remove relevant material before the reranker ever sees it.
\end{enumerate}

For these reasons, we describe the cross-encoder as a practical second-stage repair model. The main takeaway is not ``use one fixed value forever,'' but rather ``use reranking to improve ordering, and use the classifier as a soft signal instead of an aggressive filter.''

\section{Future Improvements}

The most important next step is better reranker development. The current cross-encoder already improves the top of the ranking, but its setup is still closer to a practical competition pipeline than to a deeply optimized second-stage ranking system. Future work should focus on more systematic tuning of rerank depth, candidate-set size, score calibration, and how cross-encoder scores are combined with first-stage retrieval signals. A stronger reranker model could also be explored, but the bigger goal is to make Stage 2 more deliberate instead of simply deeper.

This is also the path toward a genuinely strong information retrieval system. In a real deployment, the goal would not be to retrieve many documents and stop there. After broad candidate generation and reranking, the system should narrow the final output to a smaller and higher-quality set using explicit logic such as top-\(n\) cutoffs, score thresholds, confidence-based filtering, deduplication, category-aware constraints, or task-specific ranking rules. In that sense, the current pipeline shows a strong competition direction, but it should not yet be described as a complete production retrieval architecture.

\section{Conclusion}

We do not claim that returning \(12500\) documents would make sense in a real application. We used that depth here because the competition rewards broad coverage, not because it would be a realistic final user output. In practice, candidate generation can be wide, but the final returned set should be narrowed after reranking with explicit decision logic such as top-\(n\) cutoffs, score thresholds, confidence rules, or application-specific ranking criteria. Since careful reranker tuning is already a difficult task on its own, we leave the current system in a competition-oriented state instead of presenting it as production-ready.

The notebook and this report align with the full brief:
\begin{itemize}
    \item they present the dataset and preprocessing explicitly;
    \item they compare TF-IDF, BM25+, and embeddings directly;
    \item they evaluate embeddings structurally and visually;
    \item they add category classification with document/query comparison;
    \item they use the classifier to improve retrieval in a way that is measurable and easy to justify;
    \item they preserve a reproducible path to Kaggle submission.
\end{itemize}

Empirically, the strongest \textbf{saved offline} Stage 2 variant in the project is the embedding retriever with reranking and a soft category bonus, which reached \textbf{0.635325} in \texttt{retrieval-evaluation.ipynb}. The \textbf{submission notebook run} reports \texttt{final\_model=embedding}, \texttt{submit\_top\_k=12500}, \texttt{rerank\_top\_m=45}, \texttt{category\_bonus=0.5}, and writes \texttt{solutions\_SeaFour.csv}. The \textbf{public Kaggle score} of \textbf{0.62419} remains an external result. The main conclusion is not that every tuned value has to be copied exactly, but that the project learned the right interaction between its components: semantic retrieval gives strong candidates, the cross-encoder improves their order near the top, and the category classifier helps most when it is used as a soft signal rather than a hard filter. That is the clearest final story of the project.
