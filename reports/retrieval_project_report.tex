\section{Introduction}

Information retrieval is the task of ranking documents so that the most relevant ones appear first for a user query. In this project we work with a large technical corpus and a set of labeled training queries. The assignment is divided into two phases. Phase 1 focuses on basic retrieval with classical and neural methods. Phase 2 adds category classification and asks how the classifier can be used to improve retrieval.

The final notebook is structured around the required project questions rather than around only a single optimized run. It therefore contains:
\begin{itemize}
    \item dataset loading and statistical exploration;
    \item construction of a normalized \texttt{content} field;
    \item three retrieval models: TF-IDF, BM25+, and Sentence-Transformer embeddings;
    \item embedding inspection through matrix shapes and a 2D projection;
    \item evaluation with Recall@K, Precision@K, and MRR@K;
    \item category classification for both documents and queries;
    \item classifier-aware reranking for Phase 2;
    \item Kaggle submission export.
\end{itemize}

\section{Final Changes and Reasons}

The final submission differs from earlier draft states of the project in five important ways.

\begin{enumerate}
    \item \textbf{Ground-truth parsing was aligned with the real qrels schema.} The competition qrels store relevant items under \texttt{relevant\_doc\_ids} with nested \texttt{doc\_id} entries. Aligning the loader with that format was necessary so that Recall, Precision, and MRR reflect the true labels instead of empty relevance sets. The final notebook now also raises an explicit error if qrels parsing yields empty relevance, missing labeled-query coverage, or document ids that are absent from the corpus.
    \item \textbf{Category-wise sampling was made stable for current pandas behavior.} The notebook now uses a sampling pattern that preserves the \texttt{category} column reliably during visualization and downsampling steps. This prevents category-aware plots and classifier preparation from failing because of grouped-sampling side effects.
    \item \textbf{The query-side reporting was aligned with the actual run contexts.} Only the training queries have visible qrels, while the Kaggle test queries remain unlabeled. The report therefore separates offline Stage 2 analysis on labeled queries from the later submission direction.
    \item \textbf{The report now prioritizes impact over hyperparameter history.} Earlier draft text emphasized one supposedly ``current'' Stage 2 configuration. The revised section below instead explains which behaviors were robust across the later experiments: strong embedding recall, useful reranking, harmful hard filtering, and mild gains from a soft category bonus.
    \item \textbf{The final reporting now distinguishes three sources of truth.} The best offline Stage 2 result comes from \texttt{retrieval-evaluation.ipynb}; the current submission-code defaults come from \texttt{src/config.py} and \texttt{kaggle-submission.ipynb}; and the public score \(0.62337\) is treated as an external leaderboard result reported by the team.
\end{enumerate}

\subsection{Available fields}

Each document contains an \texttt{id} and can include \texttt{title}, \texttt{text}, \texttt{tags}, and \texttt{category}. Training queries also contain \texttt{id}, \texttt{title}, \texttt{text}, \texttt{tags}, and \texttt{category}. Test queries omit the category label because that is one of the targets of Phase 2 inference. The qrels file maps each labeled training query to a set of relevant document ids, and the final loader validates that this mapping is non-empty, aligned with \texttt{queries\_train.json}, and consistent with the document corpus.

\section{Preprocessing and Content Construction}

The assignment asks for a new text field called \texttt{content}. The final notebook uses the following policy:
\begin{itemize}
    \item documents: \texttt{title + text + tags};
    \item retrieval queries: \texttt{title + text};
    \item classifier queries in the active notebook: \texttt{title + text + tags}.
\end{itemize}

This means the project uses different query views for retrieval and for Stage 2 classification. Retrieval stays tied to the actual query wording through \texttt{title + text}, while the category classifier also consumes \texttt{tags}. That choice improved the practical submission pipeline, but it must be interpreted carefully because the query tags are highly category-informative in the labeled data.

The shared normalization steps are:
\begin{itemize}
    \item lowercasing;
    \item replacement of the separators \texttt{-}, \texttt{\_}, and \texttt{/} with spaces;
    \item whitespace collapsing;
    \item trimming leading and trailing whitespace.
\end{itemize}

For lexical methods, tokenization uses the pattern \texttt{[a-z0-9]+}, and English stopword filtering is enabled by default.

\section{Phase 1: Retrieval Models}

\subsection{TF-IDF retrieval}

TF-IDF stands for \emph{term frequency--inverse document frequency}. It gives high weight to terms that appear frequently in one document but are relatively rare in the collection. In vector-space retrieval, each document and query is represented by a sparse TF-IDF vector, and documents are ranked by cosine similarity with the query vector.

Conceptually, TF-IDF is useful because it is simple, fast, and often surprisingly competitive as a baseline. Its main limitation is that it depends strongly on lexical overlap. If a relevant document uses different wording from the query, TF-IDF may fail even when the underlying meaning is similar.

\subsection{BM25+ retrieval}

BM25+ is a probabilistic lexical ranking model. It improves over naive bag-of-words weighting by:
\begin{itemize}
    \item saturating term frequency contributions;
    \item normalizing for document length;
    \item adding a positive lower-bound adjustment through the BM25+ variant.
\end{itemize}

BM25+ is often stronger than plain TF-IDF when document lengths vary substantially, as is the case in this corpus. However, BM25+ remains a lexical model and therefore still depends on token overlap.

\subsection{Embedding retrieval}

Dense embeddings map text into high-dimensional vectors that encode semantic information. In this project we use the Sentence-Transformer model \texttt{all-MiniLM-L6-v2}. Documents and queries are embedded into a 384-dimensional space, and cosine similarity is computed through normalized dot products.

Embeddings can help retrieval because they are more robust to synonyms, paraphrases, and broader semantic similarity. Their main tradeoffs are higher computational cost, larger memory usage, and the risk of retrieving semantically related but not strictly relevant documents.

\section{Embedding Inspection and Visualization}

After generating embeddings, the notebook prints the matrix shapes for documents and queries. This directly answers the specification that the embedding structures should be examined.

To make the geometry more interpretable, the notebook also builds a 2D projection using \textbf{UMAP} when available and otherwise falls back to \textbf{t-SNE}. The plot uses a category-aware sample of documents together with the training queries. In typical runs, one should observe partial clustering by category. This is expected because categories such as \texttt{android}, \texttt{gaming}, \texttt{tex}, \texttt{unix}, and \texttt{programmers} tend to contain domain-specific vocabulary and recurrent semantic themes.

At the same time, perfect separation should not be expected. The original embeddings live in a much higher-dimensional space, some categories overlap semantically, and short queries are often more ambiguous than documents.

\section{Evaluation Measures}

The notebook implements the three required retrieval metrics:
\[
\text{Recall@K} = \frac{\# \text{relevant retrieved documents}}{\# \text{relevant documents}}
\]
\[
\text{Precision@K} = \frac{\# \text{relevant retrieved documents}}{\# \text{retrieved documents}}
\]
\[
\text{MRR@K} = \frac{1}{\text{rank of the first relevant document}}
\]

For Phase 1 comparison, the notebook also reports runtime and average latency per query. For Phase 2, it augments the retrieval summary with classifier accuracy, and computes a combined score as
\[
\text{CombinedScore} = \frac{1}{4}\left(\text{Recall} + \text{Precision} + \text{MRR} + \text{Accuracy}\right).
\]

\section{Phase 1 Experimental Protocol}

Only \texttt{queries\_train.json} has relevance labels, while \texttt{queries\_test.json} is the unlabeled competition test set. For that reason, the corrected notebook does not create a second query-side ``test split'' inside the labeled data. Instead, the labeled training queries are split into:
\begin{itemize}

This correction matters for two reasons. First, it keeps the experimental story aligned with the provided files: labeled training queries for development, unlabeled Kaggle test queries for final export. \section{Phase 2: Category Classification}

\subsection{Classifier model}

The Stage 2 pipeline uses a \textbf{TF-IDF + LinearSVC} classifier. This remains a sensible choice because the task is category prediction rather than document ranking: the classifier only needs to produce one label per query so that retrieval can exploit that label as an extra hint.

TF-IDF is a strong representation for technical categories because category membership is often signaled by highly distinctive lexical cues such as platform names, command-line terms, package names, or domain-specific jargon. LinearSVC is then a practical fit on top of that sparse representation: it is fast, reproducible, and well suited to high-dimensional text data.

What changed across the later experiments is not the classifier family, but the \emph{query representation} and how strongly the classifier is allowed to influence retrieval. In the latest evaluated Stage 2 run, query-side category prediction uses \texttt{title + text + tags}, which makes category prediction stronger but also makes it more important to interpret the classifier as a practical reranking signal rather than as a clean text-only query classifier.

\subsection{Training data choice}

The assignment explicitly asks whether both documents and queries can be used, and whether the classifier works equally well for both. In the implemented pipeline, the classifier is trained on:
\begin{itemize}
    \item a training split of the document corpus;
    \item document-side \texttt{content} built from \texttt{title + text + tags}.
\end{itemize}

On the query side, the classifier is then applied to:
\begin{itemize}
    \item all 327 labeled training queries for notebook diagnostics;
    \item all 141 Kaggle test queries for submission-time category hints.
\end{itemize}

This is important methodologically. Query tags are strongly category-informative in the labeled data. That can help the retrieval system, but it also means the classifier should be described as a practical category-hint module rather than as a neutral standalone benchmark.

\subsection{Classification metrics}

The notebook still reports query-side category accuracy, but the meaning of that number is narrower than in the older validation-based writeup. The classifier is trained on documents and then scored on the labeled training queries, so the printed accuracy is a \textbf{diagnostic sanity check} rather than a held-out Stage 2 benchmark. The more important Stage 2 question is therefore not ``what is the clean validation accuracy?'', but rather ``how does the category signal affect ranking quality?''

These results support four clear conclusions.

\begin{enumerate}
    \item \textbf{The first stage already finds most of the relevant material.} The baseline embedding system reaches Recall \(=0.947617\), so the main weakness is not coverage.
    \item \textbf{Reranking helps by fixing order near the top.} Recall and Precision stay essentially unchanged, while MRR jumps from \(0.474507\) to \(0.624435\). This is exactly the pattern expected from a good second-stage reranker.
    \item \textbf{Hard category filtering hurts because it removes candidates.} The category-filtered variant drops Recall from \(0.947617\) to \(0.880766\), which is too costly even before reranking is applied.
    \item \textbf{The category signal works best as a soft bonus.} Adding the bonus on top of reranking improves the combined score slightly, from \(0.624489\) to \(0.624939\), without the heavy recall damage caused by hard filtering.
\end{enumerate}

\subsection{Cross-encoder reranker problems}

The cross-encoder helped the project, but the important point is not that one particular value was ``the best forever.'' The important point is \emph{why} reranking helped and \emph{why} some variants failed.

\begin{enumerate}
    \item \textbf{Its benefit is rank repair, not candidate discovery.} The cross-encoder improves MRR because it reorders a strong embedding candidate set. It does not create new recall by itself; if a relevant document never enters the candidate pool, reranking cannot rescue it.
    \item \textbf{Rerank depth changes both quality and cost.} Reranking more of the list gives the cross-encoder more opportunities to repair ranking mistakes, but it also increases runtime. This is why the exact rerank depth matters mainly through its effect on how much of the head can be corrected.
    \item \textbf{The category classifier is useful as a soft signal, but risky as a hard gate.} The offline results show this directly: hard category filtering drops Recall to \(0.880766\), while a soft category bonus preserves the strong recall of the embedding baseline and still gives a small gain.
    \item \textbf{Offline gains are more optimistic than Kaggle gains.} The offline Stage 2 comparison uses labeled training queries, while Kaggle evaluates on unseen hidden queries. That is why the offline score \(0.624939\) is useful for selecting the direction of the pipeline, but the public leaderboard score remains the final external check.
\end{enumerate}

For those reasons, the cross-encoder should be described as a practical second-stage repair model. The lesson is not ``use exactly value X,'' but rather ``use reranking to improve ordering, and use the classifier softly rather than aggressively.''

\section{Future Improvements}

The most important next step is better reranker development. The current cross-encoder already improves ordering near the top of the list, but its configuration is still closer to a practical competition setup than to a deeply optimized second-stage ranking system. Future work should therefore focus on more systematic tuning of rerank depth, candidate-set size, score calibration, and the way cross-encoder scores are blended with first-stage retrieval signals. A stronger reranker model could also be explored, but the larger point is to make Stage 2 more deliberate rather than simply deeper.

This is also the path toward a genuinely strong information retrieval system. A real deployment should not stop at ``retrieve many documents and export them.'' After broad candidate generation and reranking, the system should narrow the final output to a small, high-quality set using explicit logic such as top-\(n\) cutoffs, score thresholds, confidence-based filtering, deduplication, category-aware constraints, or task-specific ranking rules. In that sense, the current pipeline demonstrates a strong competition direction, but it should not yet be described as a complete production retrieval architecture.

\section{Conclusion}

The authors acknowledge that a real information retrieval system should not expose or rely on a final output of \(12500\) documents. That depth was used here for competition-oriented performance rather than because it represents a realistic deployment target. In practical use, candidate generation can be broad, but the final returned set should be narrowed after reranking through explicit decision logic such as top-\(n\) cutoffs, score thresholds, confidence rules, or application-specific ranking criteria. Because rigorous reranker tuning is itself a difficult topic, the project intentionally leaves the current system in a competition-oriented state rather than claiming that it is already production-ready.

The final notebook and this report align with the full brief:
\begin{itemize}
    \item they present the dataset and preprocessing explicitly;
    \item they compare TF-IDF, BM25+, and embeddings directly;
    \item they evaluate embeddings structurally and visually;
    \item they add category classification with document/query comparison;
    \item they use the classifier to improve retrieval in a way that is measurable and easy to justify;
    \item they preserve a reproducible path to Kaggle submission.
\end{itemize}

Empirically, the strongest \textbf{saved offline} Stage 2 variant in the project is the embedding retriever with reranking and a soft category bonus, which reached \textbf{0.624939} in \texttt{retrieval-evaluation.ipynb}. The \textbf{current code defaults} meanwhile describe a later submission configuration with \texttt{submit\_top\_k=12500} and \texttt{rerank\_top\_m=45}. The \textbf{public Kaggle score} of \textbf{0.62337} is an external result reported by the team. The important conclusion is not that every tuned value must be copied exactly, but that the project learned the right interaction between its components: semantic retrieval provides the candidate quality, the cross-encoder repairs ranking near the top, and the category classifier helps most when used as a soft signal rather than a hard filter. That is the defensible final story of the project.
