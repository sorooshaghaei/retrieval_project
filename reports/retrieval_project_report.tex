\section{Introduction}

Information retrieval is the task of ranking documents so that the most relevant ones appear first for a user query. In this project we work with a large technical corpus and a set of labeled training queries. The assignment is divided into two phases. Phase 1 focuses on basic retrieval with classical and neural methods. Phase 2 adds category classification and asks how the classifier can be used to improve retrieval.

The final notebook is structured around the required project questions rather than around only a single optimized run. It therefore contains:
\begin{itemize}
    \item dataset loading and statistical exploration;
    \item construction of a normalized \texttt{content} field;
    \item three retrieval models: TF-IDF, BM25+, and Sentence-Transformer embeddings;
    \item embedding inspection through matrix shapes and a 2D projection;
    \item evaluation with Recall@K, Precision@K, and MRR@K;
    \item category classification for both documents and queries;
    \item classifier-aware reranking for Phase 2;
    \item Kaggle submission export.
\end{itemize}

\section{Final Changes and Reasons}

The final submission differs from earlier draft states of the project in five important ways.

\begin{enumerate}
    \item \textbf{Ground-truth parsing was aligned with the real qrels schema.} The competition qrels store relevant items under \texttt{relevant\_doc\_ids} with nested \texttt{doc\_id} entries. Aligning the loader with that format was necessary so that Recall, Precision, and MRR reflect the true labels instead of empty relevance sets. The final notebook now also raises an explicit error if qrels parsing yields empty relevance, missing labeled-query coverage, or document ids that are absent from the corpus.
    \item \textbf{Category-wise sampling was made stable for current pandas behavior.} The notebook now uses a sampling pattern that preserves the \texttt{category} column reliably during visualization and downsampling steps. This prevents category-aware plots and classifier preparation from failing because of grouped-sampling side effects.
    \item \textbf{The query split protocol was corrected.} Only \texttt{queries\_train.json} comes with visible qrels through \texttt{qgts\_train.json}, while \texttt{queries\_test.json} is the unlabeled competition test set. For that reason, presenting an internal \texttt{60 / 30 / 10} query split as train / validation / test was misleading. The corrected notebook now uses a train / validation split on labeled queries and reserves \texttt{queries\_test.json} for final export only.
    \item \textbf{The report now uses measured values instead of placeholders.} All result tables below are populated from the completed notebook outputs, with query-side evaluation on validation and document-side holdout classification kept separate.
    \item \textbf{The final active system was chosen for clarity and empirical strength.} The selected submission pipeline is the embedding retriever with the brief-aligned \texttt{text\_only} classifier, a soft category bonus, and a top-100 blended cross-encoder rerank using \texttt{cross-encoder/ms-marco-MiniLM-L6-v2}. This keeps the main assignment-visible retrieval pipeline intact while adding a small but measurable gain on the validation leaderboard score.
\end{enumerate}

Each document contains an \texttt{id} and can include \texttt{title}, \texttt{text}, \texttt{tags}, and \texttt{category}. \section{Preprocessing and Content Construction}

The assignment asks for a new text field called \texttt{content}. The final notebook uses the following policy:
\begin{itemize}
    \item documents: \texttt{title + text + tags};
    \item retrieval queries: \texttt{title + text};
    \item primary classifier queries: \texttt{title + text};
    \item classifier ablation: \texttt{title + text + tags}.
\end{itemize}

This design keeps both retrieval and the default Phase 2 classifier tied to the actual query text, which is the safer reading of the brief. Because the raw query files also contain \texttt{tags}, the notebook reports a second text-plus-tags classifier as an explicit ablation. A later leakage audit showed that the query tags are category-pure in the labeled split, so the text-plus-tags setting is methodologically closer to target leakage than to a neutral alternative query representation. The notebook therefore keeps it visible as a comparison while excluding it from the active submission path.

The shared normalization steps are:
\begin{itemize}
    \item lowercasing;
    \item replacement of the separators \texttt{-}, \texttt{\_}, and \texttt{/} with spaces;
    \item whitespace collapsing;
    \item trimming leading and trailing whitespace.
\end{itemize}

For lexical methods, tokenization uses the pattern \texttt{[a-z0-9]+}, and English stopword filtering is enabled by default.

\section{Phase 1: Retrieval Models}

\subsection{TF-IDF retrieval}

TF-IDF stands for \emph{term frequency--inverse document frequency}. It gives high weight to terms that appear frequently in one document but are relatively rare in the collection. In vector-space retrieval, each document and query is represented by a sparse TF-IDF vector, and documents are ranked by cosine similarity with the query vector.

Conceptually, TF-IDF is useful because it is simple, fast, and often surprisingly competitive as a baseline. Its main limitation is that it depends strongly on lexical overlap. If a relevant document uses different wording from the query, TF-IDF may fail even when the underlying meaning is similar.

\subsection{BM25+ retrieval}

BM25+ is a probabilistic lexical ranking model. It improves over naive bag-of-words weighting by:
\begin{itemize}
    \item saturating term frequency contributions;
    \item normalizing for document length;
    \item adding a positive lower-bound adjustment through the BM25+ variant.
\end{itemize}

BM25+ is often stronger than plain TF-IDF when document lengths vary substantially, as is the case in this corpus. However, BM25+ remains a lexical model and therefore still depends on token overlap.

\subsection{Embedding retrieval}

Dense embeddings map text into high-dimensional vectors that encode semantic information. In this project we use the Sentence-Transformer model \texttt{all-MiniLM-L6-v2}. Documents and queries are embedded into a 384-dimensional space, and cosine similarity is computed through normalized dot products.

Embeddings can help retrieval because they are more robust to synonyms, paraphrases, and broader semantic similarity. Their main tradeoffs are higher computational cost, larger memory usage, and the risk of retrieving semantically related but not strictly relevant documents.

\section{Evaluation Measures}

The notebook implements the three required retrieval metrics:
\[
\text{Recall@K} = \frac{\# \text{relevant retrieved documents}}{\# \text{relevant documents}}
\]
\[
\text{Precision@K} = \frac{\# \text{relevant retrieved documents}}{\# \text{retrieved documents}}
\]
\[
\text{MRR@K} = \frac{1}{\text{rank of the first relevant document}}
\]

For Phase 1 comparison, the notebook also reports runtime and average latency per query. For Phase 2, it augments the retrieval summary with classifier accuracy, and computes a combined score as
\[
\text{CombinedScore} = \frac{1}{4}\left(\text{Recall} + \text{Precision} + \text{MRR} + \text{Accuracy}\right).
\]

\section{Phase 2: Category Classification}

\subsection{Classifier model}

The final notebook uses a \textbf{TF-IDF + LinearSVC} classifier. This choice is motivated by the fact that Phase 2 is a \emph{classification} problem rather than a retrieval problem: given one text, the system must assign one category label.

\textbf{TF-IDF} converts each text into a sparse weighted vocabulary vector. Terms that are frequent inside one text but not frequent across the whole corpus receive larger weights. This representation is a strong fit for category prediction in this dataset because categories are often signaled by distinctive technical vocabulary. In other words, exact words such as package names, tools, commands, platforms, or domain-specific expressions often carry strong evidence about the correct label.

\textbf{LinearSVC} is a linear Support Vector Machine classifier. In practice, it learns a set of weights over the TF-IDF features and gives each class a score, then predicts the class with the highest score. Linear SVMs are a standard choice for text classification because they work very well with high-dimensional sparse vectors, train quickly, and provide a strong multiclass baseline that is easy to reproduce.

It is also useful to explain why the other project models were not used as the primary classifier. \textbf{BM25+} is fundamentally a query-document matching function, not a supervised multiclass classifier. It is well suited for ranking documents against a query, but using it for category prediction would require a more indirect design such as matching a text against category prototypes. \textbf{Dense embeddings} are excellent for Phase 1 retrieval because they reduce vocabulary mismatch and capture semantic similarity, but an embedding-based classifier would add extra modeling complexity and tuning effort here.

For this reason, the final design keeps the strongest semantic model where it matters most for retrieval, while using a lighter and more direct supervised model for category prediction. Since the classifier is used as a \emph{soft reranking signal} rather than as the main retrieval engine, \textbf{TF-IDF + LinearSVC} offers the clearest tradeoff between accuracy, speed, interpretability, and methodological simplicity.

\subsection{Training data choice}

The assignment explicitly asks whether both documents and queries can be used, and whether the classifier works equally well for both. To answer those questions directly, the notebook trains the classifier on:
\begin{itemize}
    \item a training split of the document corpus;
    \item the split-train portion of the labeled training queries.
\end{itemize}

On the query side, the corrected protocol evaluates on validation only, because \texttt{queries\_test.json} is the actual unlabeled competition test set and should not be re-described as a second offline query test split. The classifier therefore evaluates separately on:
\begin{itemize}
    \item held-out documents;
    \item validation queries.
\end{itemize}

The same trained classifier is then applied to \texttt{queries\_test.json} only to generate submission-time category hints, not offline accuracy scores. This setup still makes it possible to compare performance on long documents and short queries rather than discussing only one of them.

For the query side, the notebook now evaluates two representations on the same split:
\begin{itemize}
    \item a \textbf{text-only} variant based on \texttt{title + text}, used as the default Phase 2 setting because it stays closest to the wording of the brief;
    \item a \textbf{text + tags} variant, reported separately as an ablation because the raw JSON files do expose query tags.
\end{itemize}

This change is important methodologically. The leakage audit found no train/validation contamination and no exact duplicate overlap between split-train and validation queries, but it also showed that all query tags in the labeled split are category-pure. For that reason, if the tag-aware classifier performs better, the report can mention that result explicitly without pretending it is a clean replacement for the brief-aligned text-only model.

Instead, it comes from the tags themselves: in the labeled query set, every tag family is category-pure, which makes the tag-aware setting label-revealing in practice. We therefore keep the \textbf{text-only} query classifier as the active Phase 2 setting because it stays closer to the assignment wording and to the retrieval-side query representation. The text-plus-tags result remains a strong ablation, not a defensible default pipeline.

\section{Using the Classifier to Improve Retrieval}

The professor asks how the classifier can be integrated into the retrieval system. The final notebook uses a simple and transparent strategy:
\begin{enumerate}
    \item predict the category of each query;
    \item retrieve top-k candidates with TF-IDF, BM25+, or embeddings;
    \item normalize retrieval scores within each query;
    \item add a soft bonus to documents whose category matches the predicted query category;
    \item rerank the candidates.
\end{enumerate}

This approach is easy to justify. If the category prediction is correct, the bonus increases the likelihood that same-category documents move upward in the ranked list. If the classifier is wrong, the bonus can hurt ranking quality, which is exactly why the Phase 2 comparison must be measured rather than assumed.

In the final notebook, the main reranking path uses the \textbf{text-only} query classifier by default. The tag-aware version remains available as a reported comparison, not as an unqualified replacement for the brief-aligned setting, because its perfect query accuracy comes from label-revealing tags rather than from a cleaner modeling choice.

Two design choices deserve explanation.
\begin{itemize}
    \item \textbf{Why keep the text-only classifier?} Because it is the most defensible brief-aligned setting: the retrieval query and the classifier both rely on the actual query wording rather than on extra metadata injected at test time. The leakage audit showed that query tags are category-pure in the labeled split, so promoting \texttt{text + tags} would turn a label-revealing ablation into the main pipeline.
    \item \textbf{Why remove the extra query-side holdout split?} Because the dataset already provides labeled development queries through \texttt{queries\_train.json} + \texttt{qgts\_train.json} and a separate unlabeled competition test file through \texttt{queries\_test.json}. Calling an extra internal slice of the labeled queries ``test'' blurs that protocol and wastes scarce supervised examples.
    \item \textbf{Why export 7500 documents for submission after selecting \(K=1000\) on validation?} Because \(K=1000\) was the best depth in the offline evaluation grid, while the final CSV export still benefits from a deeper ranked list for the competition output format. The notebook therefore separates \texttt{EVALUATION\_TOP\_KS} from \texttt{SUBMISSION\_TOP\_K}.
\end{itemize}

This protocol is cleaner than fitting and evaluating repeatedly on the same labeled queries, and it matches the logic expected in a reproducible retrieval pipeline:
\begin{enumerate}
    \item develop and compare on training-derived splits;
    \item choose the best validation configuration;
    \item keep \texttt{queries\_test.json} untouched until export;
    \item export the final Kaggle file.
\end{enumerate}
